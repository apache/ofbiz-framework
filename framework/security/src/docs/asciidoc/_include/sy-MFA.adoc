= Multi-Factor Authentication (MFA) Implementation Guide
== Overview and Architecture

This guide explains how the native Multi-Factor Authentication (MFA) architecture in Apache OFBiz(R) fits together.

=== Core Capabilities

* *Native RFC 6238 TOTP Engine:* Zero-dependency TOTP generation and verification built directly on standard JDK `javax.crypto.Mac` (HmacSHA1, HmacSHA256, HmacSHA512) and pure RFC 4648 Base32 codec in `org.apache.ofbiz.security.login.TotpUtil`.
* *NIST SP 800-63B Emergency Backup Recovery Codes:* Generates 10 single-use, 8-character Crockford Base32 recovery codes (`xxxx-xxxx`) stored with salted cryptographic hashing (`secretHash`) and atomic invalidation (`thruDate = nowTimestamp()`), preventing customer lockouts on eCommerce storefronts.
* *Email Password Recovery Does Not Bypass MFA:* `emailPasswordRequest` sends the normal password-reset email to MFA-mandated accounts exactly as it does to anyone else -- it is **not** blocked, because doing so would only strand customers who still have their authenticator but simply forgot their password, without closing any real gap: `LoginWorker#login()` re-evaluates the MFA policy for *every* successful primary authentication, including a password-reset-token login, and will not commit a session without the second factor regardless of how the password was changed. The weaker, legacy password-*hint* path (`showPasswordHint`) remains blocked for MFA-mandated accounts, since a stored hint is not an acceptable authenticator under NIST SP 800-63B and offers no real recovery value once backup codes exist. A lost *authenticator device* (not merely a forgotten password) with no remaining backup codes still requires administrator-assisted recovery (see the `mfaAdministrativeReset` path above) -- this is standard practice (Google, GitHub, AWS all require either a backup code or support-assisted recovery in that scenario).
* *Staged Authentication Lifecycle:* `PRIMARY_VERIFIED` -> `MFA_PENDING` -> `AUTHENTICATION_COMMITTED` strictly eliminates pre-MFA session state poisoning, premature login history commits, and improper lockout resets.
* *Zero-Trust Session Isolation:* Guarantees that neither an authenticated HTTP session (`userLogin` attribute), login cookies, nor successful `UserLoginHistory` records are committed before the second factor succeeds.
* *Air-Gapped In-Memory PNG QR Generation:* Generates QR codes natively in-memory as Base64-encoded PNG Data URIs (`data:image/png;base64,...`) via `com.google.zxing:core` and standard `javax.imageio.ImageIO`, ensuring zero-CDN dependency, air-gapped security, and universal cross-browser compatibility without SVG XML injection vulnerabilities.
* *Role & Group-Level Policy Enforcement:* Seamless self-service setup under user profiles and mandatory forced-enrollment interstitials for high-privilege security groups (`SecurityGroup.requireAuthFactor="Y"`).
* *High-Assurance Re-Authentication Windows:* 300-second (5 minutes) validity window protecting sensitive mutations (password modifications), with in-session re-authentication (`/reverifyAuthFactor`) avoiding forced logouts.
* *Two-Step REST API Token Handshake:* Outbound tokens emit RFC 8176 standard `amr: ["pwd", "otp", "mfa"]`, while inbound tokens from external Identity Providers (Keycloak, Okta) support configurable `amr` and `acr` assurance evaluation.
* *Comprehensive Security Auditing:* Dedicated `UserAuthenticationEvent` entity capturing precision timestamps, actor IDs, challenge IDs, event types, and mandatory administrative justifications.
* *100% Backward Compatibility:* Master toggle disabled by default (`security.login.authFactor.enable=false`), guaranteeing zero impact on existing test suites, internal service calls, or legacy password-only deployments.

=== 1. Data Model & Entity Architecture

The implementation introduces four additive entities in `framework/security/entitydef/entitymodel.xml` with zero schema changes to existing core entities:

==== UserLoginAuthFactor
Stores configured authentication factors:
* `factorId` (id, PK): Unique factor identifier.
* `userLoginId` (id-vlong, FK): Owner of the authentication factor.
* `factorType` (id): Factor type indicator (`ULAF_TOTP`, `ULAF_BACKUP`, `ULAF_WEBAUTHN`, `ULAF_PASSKEY`).
* `secret` (long-varchar, encrypt="true"): AES-encrypted shared secret (or COSE public key for WebAuthn).
* `secretHash` (long-varchar): Salted cryptographic hash for backup recovery codes (`HashCrypt.cryptUTF8`) or Base64URL `credentialId` for WebAuthn.
* `factorLabel` (description): User-friendly label (e.g., "Work Mobile Authenticator", "Backup Recovery Code").
* `needsValidation` (indicator): 'Y' during pending enrollment; transitions to 'N' only upon successful verification.
* `lastUsedDate` (date-time): Timestamp of last successful verification.
* `lastUsedStep` (numeric): Monotonic counter field. Stores accepted RFC 6238 time-step (replay defense) or FIDO2 Signature Counter (`signCount`) for authenticator clone detection.
* `fromDate` / `thruDate` (date-time): Lifecycle validity window. Atomic consumption of backup codes sets `thruDate = nowTimestamp()`.

==== UserLoginAuthChallenge
Ephemeral, server-managed authentication challenge record:
* `challengeId` (id, PK): Cryptographically random identifier issued to the client.
* `userLoginId` (id-vlong, FK): Identity bound to this challenge.
* `factorId` (id, FK): Target factor selected for verification.
* `sessionBindingHash` (long-varchar): Cryptographic session binding hash (or WebAuthn binary challenge).
* `challengeStatus` (id): `PENDING`, `CONSUMED`, `EXPIRED`, `LOCKED`.
* `attemptCount` (numeric): Incremented on failed verification attempts.
* `createdDate`, `expiresDate`, `verifiedDate` (date-time): Challenge lifecycle timestamps (default TTL: 300 seconds).

==== UserAuthenticationEvent
Append-only security audit entity:
* Captures events: `MFA_ENROLL`, `MFA_VERIFY_SUCCESS`, `MFA_VERIFY_FAILURE`, `MFA_FACTOR_REVOKED`, `MFA_BACKUP_CODES_GENERATED`, `MFA_ADMIN_PASSWORD_RESET`.
* Records `actorUserLoginId`, `eventReason` (mandatory administrative reason up to 255 chars), and precision `eventDate`.

==== SecurityGroup Extension
* `requireAuthFactor` (indicator): Added to `SecurityGroup` entity ('Y'/'N', default 'N'). When enabled on any active group, all users with active membership are subject to mandatory MFA enforcement.

=== 2. Authentication Channels & Policy Matrix

[cols="2,2,3,2,2", options="header"]
|===
| Channel | Entry Point / Handler | Behavior When MFA Is Required | State & History Timing | Policy & Edge Cases

| *1. Standard Web UI* (Form Login)
| `LoginWorker.login()` (`common-controller.xml`)
| `userLoginMfaPending` validates password. Session set to `_MFA_PENDING_`. User redirected to `authFactorChallenge` view. Code verified via `MfaServices.verifyUserLoginMfaChallenge`.
| `userLogin` attribute kept null in session. Successive failed logins increment on bad OTP. `UserLoginHistory` and session commitment occur only upon Step 2 success.
| Forced enrollment triggered if user lacks active factor. Double session rotation executed.

| *2. Service-Level Login* (`isServiceAuth`)
| `LoginServices.userLogin()` / `userLoginMfaPending()` (`DispatchContext`)
| Scheduled background jobs, ECA rules, and inter-service SOAP/HTTP calls pass `login.username` and `login.password` in service context map. Interactive challenge is not possible.
| `userLoginMfaPending` strictly rejects service authentication for MFA users with `ServiceUtil.returnError()`. No session established; no history written.
| *System accounts (`isSystem='Y'`) are explicitly exempt.* Interactive human accounts cannot run automated background services.

| *3. REST API* (Token Handshake)
| `AuthenticationResource.java` (`/rest/auth/token` & `/rest/auth/{group}/mfa/{id}/verify`)
| Two-step handshake: Step 1 validates Basic Auth and returns HTTP 202 `Accepted` with ephemeral `challengeId`. Step 2 accepts OTP/backup code and mints JWT bearer tokens.
| `HttpBasicAuthFilter` defers `UserLoginHistory` to Step 2. Failed OTP attempts increment `successiveFailedLogins`. `UserLoginHistory` committed at Step 2.
| Pre-validates API group binding and `baseSecurityGroupPermission` to prevent cross-group token theft.

| *4. JWT SSO* (Federated IdP)
| `JWTManager.checkJWTLogin()` (preprocessor)
| Inbound JWT tokens from external IdPs (Keycloak, Okta) are evaluated for trusted `amr` (`otp`, `mfa`, `fido`, `hwk`) or trusted `acr` claims. If assurance is present, the token is accepted immediately.
| **Known limitation, confirmed by live testing:** if assurance is missing, `checkJWTLogin` correctly creates the challenge and returns `authFactorRequired`/`authFactorEnrollmentRequired` -- but this runs as a controller *preprocessor* event, and `RequestHandler`'s preprocessor loop (core OFBiz, unrelated to this PR) only honors a `success` return from preprocessor events; any other value is logged and discarded. The challenge is created server-side but never shown, so the request silently falls through unauthenticated instead of prompting for a second factor.
| `security.jwt.mfa.amr.trusted` and `security.jwt.mfa.acr.trusted` configure trusted identity providers. Only affects JWT-authenticated users who already have an active factor or are in an MFA-mandated security group; non-MFA users are unaffected.

| *5. HTTP Header, Remote-User/Tomcat SSO & Client Certificate* (Proxy / mTLS)
| `LoginWorker.checkRequestHeaderLogin()`, `checkServletRequestRemoteUserLogin()`, `check509CertLogin()` (all preprocessors) -> `loginUserWithUserLoginId()`
| Reverse proxy, servlet-container SSO, or TLS layer asserts primary identity for `REMOTE_USER`, Tomcat SSO, or an X.509 client certificate.
| **Same known limitation as JWT SSO above, verified by live `curl` testing against this branch:** when MFA is required, `loginUserWithUserLoginId` returns `authFactorRequired`, but since all three entry points above are controller preprocessors, that return value is swallowed by `RequestHandler` the same way, and the challenge is never shown. The user is left effectively anonymous for that request rather than being prompted or rejected.
| Configurable perimeter trust: `security.login.http.header.mfaTrusted=false` by default. **This is a pre-existing OFBiz `RequestHandler` preprocessor constraint, not something introduced or fixed by this PR; it would need either a core framework change (letting preprocessors render a view) or moving these checks off the preprocessor chain to resolve.** Only affects users who already have an active factor or are in an MFA-mandated security group; non-MFA users authenticate normally through these channels.

| *6. External Login Key* (Cross-App SSO)
| `ExternalLoginKeysManager.java` (`externalLoginKey`)
| Navigating across OFBiz web applications generates a transient single-sign-on ticket. Ticket carries the verified `_MFA_VERIFIED_AT_` timestamp.
| Target application imports verified timestamp into its session. `UserLoginHistory` already written by origin app.
| Eliminates duplicate MFA challenges during valid cross-webapp navigation while enforcing 300s re-authentication window. Transient URL key lifetime remains tightly bounded at 2 minutes. This channel is not subject to the preprocessor limitation described in rows 4 and 5: `checkExternalLoginKey` never itself decides whether MFA is required -- it only forwards an already-verified timestamp (or none) and always returns `success`, deferring any fresh MFA decision to the normal Standard Web UI flow on the next request.
|===

=== 3. Standards Compliance & WebAuthn / Passkeys Extensibility

==== RFC 8176 Compliance (Authentication Method Reference)
* In IANA / RFC 8176, `"totp"` is not a registered AMR value. The official standard registers `"otp"` (One-Time Password) for all OTP types (RFC 6238 TOTP, RFC 4226 HOTP, and lookup recovery codes) and `"mfa"` for multi-factor authentication events.
* Tokens minted post-MFA by `/rest/auth/{apiGroup}/mfa/{challengeId}/verify` strictly emit:
** `amr: ["pwd", "otp", "mfa"]` for TOTP (`ULAF_TOTP`) and Backup Codes (`ULAF_BACKUP`).
** `amr: ["pwd", "fido", "mfa"]` for WebAuthn / Passkeys (`ULAF_WEBAUTHN`, `ULAF_PASSKEY`).
* `security.jwt.mfa.amr.trusted=mfa,otp,totp,sms,hwk,fido` guarantees backwards compatibility while adhering strictly to IANA/RFC 8176 standards.

==== Future-Proof WebAuthn / Passkeys (FIDO2) Architecture Mapping
The existing data model is designed to support WebAuthn / Passkeys out of the box with zero database schema migrations:
1. `UserLoginAuthFactor.factorType`: Maps to `ULAF_WEBAUTHN` or `ULAF_PASSKEY`.
2. `UserLoginAuthFactor.secret`: Encrypted storage for the Authenticator's Credential Public Key (in COSE format or PEM).
3. `UserLoginAuthFactor.secretHash`: Indexed lookup for the Base64URL-encoded `credentialId` returned during `navigator.credentials.get()`.
4. `UserLoginAuthFactor.lastUsedStep`: Monotonic numeric column directly stores the FIDO2 Signature Counter (`signCount`) to detect cloned authenticators (`signCount > lastUsedStep`).
5. `UserLoginAuthChallenge.challengeId` / `sessionBindingHash`: Holds the cryptographically random binary challenge passed to `navigator.credentials.get()` / `create()` to guarantee freshness and prevent replay attacks.
6. `UserLoginAuthChallenge.attemptCount`: Limits assertion attempts against brute-forcing.

=== 4. Operational Configuration

All operational toggles reside cleanly in `framework/security/config/security.properties`:

[source,properties]
----
# =================================================================
# Multi-Factor Authentication (MFA) Configuration
# =================================================================

# Master switch: false by default to ensure 100% backward compatibility
security.login.authFactor.enable=false

# Issuer name displayed in authenticator applications (e.g., Google Authenticator)
security.login.authFactor.totp.issuer=Apache OFBiz

# Lifetime of an unverified MFA login challenge in seconds
security.login.authFactor.pendingTimeout=300

# Maximum failed verification attempts before challenge lockout
security.login.authFactor.maxVerifyAttempts=5

# Step-up re-authentication window for sensitive actions (5 minutes)
security.login.authFactor.reauthenticationWindow=300

# Number of emergency single-use backup recovery codes generated per user
security.login.authFactor.backupCodes.count=10

# Trusted RFC 8176 AMR claim values for JWT assurance evaluation
security.jwt.mfa.amr.trusted=mfa,otp,totp,sms,hwk,fido

# External perimeter proxy MFA trust toggles (default: false)
security.login.http.header.mfaTrusted=false
security.login.tomcat.sso.mfaTrusted=false
----

=== 5. Automated Test Suites & Verification

The implementation is verified by comprehensive automated test suites:
1. `UserLoginTests.groovy` (9/9 Integration Tests Passing): Staged authentication deferral, single-use challenge consumption, factor masking, service engine rejection, forced enrollment, 300s password change gating, audit reason logging, and NIST SP 800-63B backup code generation and consumption.
2. `TotpUtilTests.java` (4/4 Unit Tests Passing): All 6 official IETF RFC 6238 Appendix B Table 1 test vectors across SHA-1, SHA-256, and SHA-512, 1-step window matching (±30s) at the library level, and Base32 codec. The window size `MfaServices` passes down is configurable via `security.login.authFactor.totpWindowSteps` (default `1`), not hardcoded.
3. `AuthenticationContextTests.java` (10/10 Unit Tests Passing): RFC 8176 AMR evaluation (`otp`, `mfa`, `fido`, `totp`), single-factor password rejection, external login key assurance propagation, and perimeter header SSO trust checks.
4. `MfaNotificationAndRestTests.java` (Passing): REST API two-step challenge verification, RFC 8176 `amr: ["pwd", "otp", "mfa"]` token assurance, and security alert notifications.
5. `JWTManagerAssuranceTests.java` (5/5 Unit Tests Passing): JWT token minting, claim extraction, and end-to-end cryptographic token validation with RFC 8176 assurance claims.
6. `LoginEventsTests.java` (Passing): Proper propagation of MFA challenge status codes (`authFactorRequired`, `authFactorEnrollmentRequired`) through storefront and application wrappers.
